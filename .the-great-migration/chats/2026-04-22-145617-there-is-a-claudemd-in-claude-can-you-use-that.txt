   etc-spring-boot, invoked by the Entitlement sync scheduler.
  - (c) Custom scheduled task — if the rule is time-windowed, multi-join, or

  D6 — Tickets stay in Jira; workspace holds a thin SupportTicket Object that 
  references Jira

  Today: Support workspace treats Jira as the authoritative ticket system. Three
   Jira projects: LRHC (Help Center), LRFLS (First Line Support), LSV (Security
  Vulnerabilities). Attachments go to GCS, referenced from Jira comments.
  Zendesk references linger as dead fields (zendeskTicketId).

  Provisioning creates Zendesk tickets today for new subscription notifications
  and error conditions — it's the last active Zendesk consumer.

  Proposal:
  - SupportTicket Object — thin wrapper around a Jira issue. Fields:
  accountEntryId, jiraIssueKey, jiraProject, subject, statusCached,
  priorityCached, lastSyncedAt. Acts as the workspace's handle on a ticket for
  reporting, account-scoped views, and Object Actions.
  - Zendesk retired entirely. Provisioning's subscription-notification and
  error-ticket flows move to Jira (new JSM project or reuse existing).
  - Attachments stay in GCS via the existing TicketAttachment Object pattern.

  The concerns:

  1. State drift. If statusCached/priorityCached live on the Object, they can
  fall out of sync with Jira. Options: (i) don't cache, query Jira live every
  render; (ii) sync via Jira webhook; (iii) sync nightly. The Support workspace
  today uses @Cacheable with scheduled eviction, which is option (iii). Fine,
  but the staleness window needs a policy.
  2. Jira project for Provisioning's tickets. Today Provisioning → Zendesk
  creates tickets with custom fields tied to Zendesk's field IDs. Moving to Jira
   means picking a project and mapping fields. Could reuse LRFLS (fits — "new
  customer onboarding" is first-line-support-ish) or create a new project.
  Decision for the operations team.
  3. Historical Zendesk tickets. Support has zendeskTicketId on
  TicketAttachment. Archive those rows separately; don't migrate them into the
  new ticket flow.

  My call: keep Jira-native, retire Zendesk, cache status with webhook-driven
  sync (option ii) — webhooks are less wasteful than nightly re-pull and avoid
  the every-render Jira load.

  Keep, change, or discuss?

  Today: Provisioning_LicenseKey in the prov DB has 230,466 rows. The audited
  osb-provisioning source does not declare this table — some sibling module or
  adjacent service owns it (open question in audit). OSB_LicenseKey (legacy) has

  Proposal:
  - LicenseKey Object with fields: key (unique indexed), subscriptionId,
  productVersion, startDate, endDate, maxServers, maxDevelopers, status.
  - Generation as an Object Action on Subscription state transitions (e.g.,
  Trial → Active).
  - Migration: extract all 230K active rows from Provisioning_LicenseKey into
  the new Object. Legacy OSB_LicenseKey rows archive separately (201K rows that
  may or may not still be valid).

  1. Ownership question is a blocker. We can't write the generation logic
  without finding the current implementation. The audit surfaced this — 230K

  osb-provisioning-license* module, a separate OSB app, or an LCS-side service.

  Provisioning_CommonLicenseKey (476) in the same DB look related. May be part
  of the same module. Whatever owns LicenseKey probably owns these too.

  against. Whatever algorithm generates them today has to port identically, or
  existing installs stop validating.

  My call: LicenseKey Object, generation as Object Action, conditional on 
  finding the current implementation. Add to the open-risks list as a phase-3
  blocker.

  D13 — Service-to-service auth = OAuth2 client credentials; retire Koroneiki's

  matters for audit, we either (a) preserve the pattern as optional request

  authorization-code flow for UI-driven actions so the user identity is captured
   natively.
